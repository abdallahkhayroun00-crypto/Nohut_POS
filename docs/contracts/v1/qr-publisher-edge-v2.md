# Cloud QR Publisher v2 — owner-approved design

Status: **Proposed implementation contract / not deployed**. Owner decision 2026-11-28 supersedes v1's Windows-only GitHub key location (not its Windows data authority, authorization, or secret-exclusion rules). Existing public QR repository remains view-only; this change does not edit it.

## Trust and routing
- Windows is the single authoritative offline-first POS, catalog draft and command executor. Android/PWA use existing qr_menu_write/publish/reconcile/image/sync commands and grants. No independent phone/cloud draft writer.
- Edge Function `qr-publisher` replaces the loopback publishing transport after verification. Only a valid, active restaurant-scoped Windows agent may submit an execution request bound to its current authority lease/epoch, original authorized actor, command receipt and confirmed expected draft stamp. Validate these server-side using private RPCs with existing control-plane authorization; never trust client-supplied actor/role/restaurant. No public service-role key, static shared password or client GitHub token.
- Preserve existing menu grants; explicit publish confirmation and conflict handling. Revoked sessions/grants/devices and expired/superseded Windows authority fail closed, including at execution. Read-only health exposes no secrets.
- Store GitHub App RSA private PEM as Supabase Edge Function secret `NOHUT_QR_GITHUB_PRIVATE_KEY`; app ID `NOHUT_QR_GITHUB_APP_ID`; optional verified installation ID `NOHUT_QR_GITHUB_INSTALLATION_ID`. Never store in synced rows, client config, installer, backup, logs or response. Prefer PKCS#8 conversion in memory or supported audited RS256 library accepting GitHub-generated PEM. Short-lived JWT and installation token remain server-only; repository-scoped token with contents:write, installation restricted to QR repo. No other repo access.

## Fixed GitHub boundaries
- Hardcode `nohutfalafel/qr-menu`, branch `main`, host api.github.com, managed file `cms/pos-managed-menu.json`, bootstrap `cms/catalog-v1.json`, marker `cms/pos-managed-status.json`. No caller-controlled repository, branch, target URL or arbitrary path.
- Match server.mjs validation/identity invariants, TR/EN/AR strings, money, active/availability flags and stable IDs. Strict allowlists, bounded bodies and content-type, image magic-byte validation; server-derived content-addressed image path under assets/products/pos-* only. Never accept SVG upload or traversal. Use existing publisher public marker; no implicit first activation.
- Atomic Git Data commit for catalog and marker when needed, conditional non-force branch ref update based on observed parent SHA; handle competing writers via conflict, never force. Require explicit reviewed publication for first activation. No silent edits to unrelated paths. Separate GitHub commit success from Pages deployment readiness.
- Existing /catalog response revision+catalog; publish result includes revision, commit, requestId and status. Record durable server-side request identity (restaurant, command receipt, canonical payload hash, expected revision); same id+payload returns recorded outcome, different payload conflicts. Persist intent before external side effect. Distributed concurrency claim/lease, not in-memory lock. Stable request marker in commit and reconciliation by actual remote commit/tree after lost response. Unknown outcome blocks retries until resolved; do not claim success based only on accepted request. No overwriting newer changes. Audit actor/device/epoch, request ID, revision, commit, time, result, no credentials or full payload in logs.
- Route image requests with same auth/idempotency constraints; keep private temp/upload storage bounded and cleanup. Existing public menu auto-sync every ten minutes and historical prices unchanged.
